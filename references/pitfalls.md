# 踩坑清单

两轮收割（第二轮实跑 1470 份材料、4695 次执行、复现 159 条）沉淀下来的。脚本里能固化的已经固化，这里记原因，方便改脚本时别改回去。

## 选题

- **要求有已合并关联 PR** 是锁根因的唯一办法。同一套流程两轮对比：

  | | 不筛关联 PR | 要求已合并 PR |
  |---|---|---|
  | 池子 | 3903 | 1206 |
  | 正文自带 SQL | 41% | 75% |
  | 复现 | 121 | 159 |
  | 根因覆盖 | 事后满世界找，90% | 进池前 100% |

- **关联 PR 端点 `/issues/{n}/pull_requests` 是最容易被忽略的一步**。前期只抓 issue+评论，找根因绕了一大圈词面匹配，正向关联一直挂在详情页上。
- **关联 PR 近一半属于 Plugin 仓**（B 兼容缺陷的修复主体在 dolphin）。Plugin 仓 PR 要单独抓（`fetch.py pulls-plugin`）。
- **不要用 dbdogFit / buildCost / groundTruth 分档当过滤器**。关键词分误杀严重，比如 `COST_HEAVY` 里有「升级」，正文一句「升级到 X 后出现」的纯 SQL 缺陷就被判成单机造不出。只配排序。
- **版本也不要当过滤器**。issue 标的影响版本经常对不上实际能复现的版本。
- 老数据的关联 PR 没有 `repo` 字段。按号+标题回 `pulls.jsonl`/`pulls_plugin.jsonl` 定仓，定不了（多半是 docs 仓）就标空，**绝不默认成 server 仓**。

## 抽取（scripts/sqlextract.py，每条都有回归用例）

- **PL/SQL 体不能按 `;` 切句**：`CREATE PROCEDURE ... BEGIN x:=1; ... END;` 第一个内部分号就腰斩，DB 回 `subprogram body is not ended correctly`。进入 PL 体后靠 begin/end 深度配对收口。实测这一条占构造失败最大头：修好后该类报错 369 → 82 个版本格。`if not exists` 里的 `if` 不开块。
- **判「缓冲区为空」要忽略空白行**，否则 `declare` 前一个空行让块识别整体失效——而且聚合指标还在变好，一度没发现。
- **不能「有围栏块就只信围栏」**：OG-7097 的 SQL 在模板操作步骤里，围栏放的是 gdb 堆栈。按正文顺序围栏内外都扫，靠语句级去重（压空白+小写）防重复取材——重复取材会跑出满屏 `already exists`。
- `DO $$…$$;` 之后多写一行 `/`，gsql 当独立语句报错**并吞掉后面所有判读语句**。
- 一行多条（`drop ...;create ...;`）要拆；SQL 关键字开头的新行要断句，否则前面的散文粘上建表语句整句被丢。
- 以 SQL 关键字开头的行即便带中文也要留；系统表（`pg_*`/`gs_*`/`dbe_*`/`information_schema`）不算要自己建的对象。
- **改抽取器后要对具体 issue 做前后 diff，不能只看聚合指标**。踩过两次：一次 heredoc 多重转义把正则写成 `\\s`，修复空转三轮而指标还在变好；一次过滤 gsql 回显把 PL 块里独占一行的 `begin` 当 banner 删了。

## 兼容模式

1. **按 SQL 语法指纹派库**，大多数 issue 不写「B 兼容」。补上指纹后多认出 39 条。
2. **建了 B 兼容库不等于 B 语法能用**：还要 `SET enable_set_variable_b_format=on`，否则 `@变量`、反引号一律 syntax error。149 条用例因为缺它没跑到触发点。跑批前导已自动加。
3. **跑之前确认库真的存在**。`bench_d` 一度没建，10 条 D 兼容用例连库都没连上，输出 480 字节被记成「跑通」。`preflight.sh` 查库，`worker.sh` 用「一行 `Time:` 都没有」报 noexec。

## 跑批

- 临时文件名必须带 worker 序号。
- **`while read` 循环里的 `su`/`ssh` 会吃掉管道剩余输入**，worker 提前「读完」退出。症状：多个 worker 停在同一个数字。所有 `su` 都要 `< /dev/null`。
- 每条前后探活；拉不起来**只跳过这一条**，绝不 `break`——一条 MOT 用例打挂实例后剩下 61 条一条没跑。
- **现役实例不重启但也不能直接放弃**：`revive=wait` 只等它自己恢复（postmaster 会自行重启），不 systemctl，也不因一次崩溃把剩下几百条全 SKIP。
- core 每实例只留最新一个。
- 需要 gs_dump / 改参数重启的**串行单独跑**（`run_shell.sh`），别和 SQL 批混。
- `~/.og_env` 常是 `PATH=...:$PATH` 追加式，**只能 source 一次**。放进循环几千轮后 execve 报 `Argument list too long`，灌载窗口被静默截断（180 秒 RUNS_OK 从 5042 掉到 3852）。

### 跑批前必须清的残留（`preflight.sh --clean`）

- **FOR ALL TABLES 的逻辑复制发布**：无 replica identity 的表 UPDATE/DELETE 一律被拒。实测最毒，四个判读 agent 从不同分片独立指认它。
- **用例留下的 DDL 审计事件触发器**：别的用例报 `permission denied for relation <审计表>`。
- `c<数字>` 前缀的残留 schema。

## 判读

- 报错型要机制对得上；期望结果不对却报语法错 = 版本不支持该语法。
- **并行跑批的崩溃归属不可信**：实测 38 个崩溃候选隔离后 17 个是真的、21 个是连带假阳性。
- 构造失败/缺依赖单独归类，不混进「不复现」。
- 判读会揪出一批**我们自己脚本的 bug**（引用不存在的系统表列、`SET ROLE` 缺口令、对照组自己报错、setup 一行没灌进去）。修完重跑，实测净赚 12 条复现。

## 溯根因

- 顺序：关联 PR → PR【根因分析】+【实现方案】（只看前者漏 520 个）→ PR 标题 → issue 评论（读语义，正则扫规范措辞会漏三分之二）→ 源码。
- **拿报错文本去匹 PR 描述没用**：9176 条 PR 只匹出 2 条且全是假匹配。
- **跨仓同号**：踩过两次——一次 38 条根因里 12 条错，一次 231 个修复 diff 里 79 个抓错。
- **PR 正文误粘模板**：标题讲 A 正文讲 B，已发现 5 例以上，只信标题。
- **修复藏在默认关闭的 GUC 后面**（`sql_beta_feature`、`handle_toast_in_autovac`、`behavior_compat_options`）：默认配置下仍复现不代表社区没修。
- **复现不等于是缺陷**：复现集里约 27% 社区判「已取消」，标 `NON_DEFECT=cancelled` 留作负样本。
- 别用根因文字长度定 GT：试过「超过 60 字给 GT=3」，GT=3 占比虚高三倍，61 条要降档。

## 沉淀

- 目录名和对象名都是题面泄漏面：被测 agent 看到表名 `c6939_t` 会直接说「这就是 issue 6939 的复现表」然后去搜社区结论。对象名换成 `sha256` 别名，映射只存 `_alias-map.json`，不进 prompt。
- 题面（`phenomenon`）里的根因词同样是泄漏，写完要自查。

## 铁律

- 关键词规则只配排序，不配判定。判「有没有根因」「是不是同一缺陷」一律交给模型读语义。
- 穷尽正向数据源（关联 PR、PR 栏位、评论）再做反向推断。
- 「跑通没报错」和「压根没跑」长得一样，必须有自动告警。
